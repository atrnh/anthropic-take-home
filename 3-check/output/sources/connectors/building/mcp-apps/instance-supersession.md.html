1 > ## Documentation Index2 > Fetch the complete documentation index at: https://claude.com/docs/llms.txt3 > Use this file to discover all available pages before exploring further.4 5 # Supersede older widget instances6 7 > Keep only the newest copy of a widget active when its tool is called more than once in a conversation8 9 Each time Claude calls a tool that renders an MCP App, a separate iframe is mounted in the conversation. There is no host API to unmount earlier instances when a newer one appears, so by default you end up with several live copies of the same widget, each independently pushing [model-context updates](https://modelcontextprotocol.github.io/ext-apps/api/classes/app.App.html#updatemodelcontext) (data the widget feeds into Claude's context for the next turn) and [messages](https://modelcontextprotocol.github.io/ext-apps/api/classes/app.App.html#sendmessage) to Claude.10 11 If your widget represents a single piece of state, such as a shopping cart or a dashboard, only the most recent instance should remain interactive. You can use [`BroadcastChannel`](https://developer.mozilla.org/docs/Web/API/BroadcastChannel) to make earlier instances disable themselves.12 13 The snippets on this page assume you have registered a UI resource and tool and created an `App` instance from `@modelcontextprotocol/ext-apps`. See the [SDK Quickstart](https://modelcontextprotocol.github.io/ext-apps/api/documents/Quickstart.html) if you haven't.14 15 ## How it works16 17 All widget iframes from a single connector are served from the same sandbox origin on `*.claudemcpcontent.com` (the iframe sandbox includes [`allow-same-origin`](https://developer.mozilla.org/docs/Web/HTML/Element/iframe#sandbox)). That means a `BroadcastChannel` opened in one instance reaches every other instance from the same connector in the current conversation. See [Channel scope and `ui.domain`](#channel-scope-and-ui-domain) for how a fixed domain widens this.18 19 The pattern has three parts:20 21 1. **The server stamps each tool result with an election key.** It returns a `{createdAt, seq}` pair (server wall-clock time and a monotonic counter) in [`structuredContent`](https://modelcontextprotocol.io/specification/latest/server/tools#structured-content), the typed JSON payload slot of an MCP tool result. Tool results are stored in the conversation transcript, so every device and every remount of the widget sees the same key.22 2. **Each widget announces its key on a shared channel.** Shortly after `connect()` resolves, the host delivers the tool result that mounted this widget (including its `structuredContent`) via the SDK's [`toolresult` event](https://modelcontextprotocol.github.io/ext-apps/api/types/app.AppEventMap.html). The widget reads its key from that event, opens a `BroadcastChannel`, and broadcasts the key.23 3. **Any widget that sees a younger sibling marks itself superseded.** It greys out its UI, disables its buttons, and short-circuits all calls that mutate model context or inject messages.24 25 ## Mint the election key on the server26 27 Use [`registerAppTool`](https://modelcontextprotocol.github.io/ext-apps/api/functions/server-helpers.registerAppTool.html) to register the tool, and return the key in `structuredContent` alongside your normal tool output. A per-process counter works for a demo; a production server should derive the key from something durable, such as a database row ID or a version number on the underlying record.28 29 ```ts theme={null}30 import { registerAppTool } from "@modelcontextprotocol/ext-apps/server";31 import { z } from "zod";32 33 let callSeq = 0;34 35 registerAppTool(36   server,37   "show_cart",38   {39     title: "Show cart",40     description: "Render the user's shopping cart as an interactive widget.",41     inputSchema: { items: z.array(z.string()).optional() },42     _meta: { ui: { resourceUri: "ui://cart-demo/cart.html" } },43   },44   async ({ items }) => {45     const list = items ?? [];46     const seq = ++callSeq;47     const createdAt = Date.now();48     return {49       content: [{ type: "text", text: `Cart rendered with ${list.length} item(s).` }],50       // The election key travels with the tool result in the transcript,51       // so rehydrated widgets on any device recover the same ordering.52       structuredContent: { items: list, seq, createdAt },53     };54   },55 );56 ```57 58 ### Why not use client-side `Date.now()`?59 60 Client mount time does not reflect tool-call order. When a stored conversation is reopened, Claude lazy-mounts widget cells as they scroll into view, so an older widget can mount after a newer one and would win an election based on client timestamps. The server-minted key is written into the transcript at tool-call time and is identical everywhere.61 62 ## Run the election in the widget63 64 The four snippets in this section form a single module; paste them in order into your widget entry file.65 66 ### Read the key from the `toolresult` event67 68 Connect and read the values you need from the host: your instance ID from [`hostContext.toolInfo`](https://modelcontextprotocol.github.io/ext-apps/api/interfaces/app.McpUiHostContext.html#toolinfo), and the server-minted key from the `toolresult` event. The event's `structuredContent` is typed `Record<string, unknown>`, so cast it to the shape your server returns.69 70 ```ts theme={null}71 import { App } from "@modelcontextprotocol/ext-apps";72 73 type CartResult = { items?: string[]; createdAt?: number; seq?: number };74 75 const app = new App({ name: "cart-demo", version: "1.0.0" });76 77 let superseded = false;78 let keyFinalized = false;79 let orderKey: number | undefined;80 let seq: number | undefined;81 let items: string[] = [];82 83 app.addEventListener("toolresult", (params) => {84   const sc = params.structuredContent as CartResult | undefined;85   if (sc?.items) items = sc.items;86   if (sc && Number.isFinite(sc.createdAt)) {87     orderKey = sc.createdAt;88     seq = Number.isFinite(sc.seq) ? sc.seq : undefined;89     keyFinalized = true;90     announce(); // defined in "Broadcast and compare on a shared channel" below91   }92 });93 94 await app.connect();95 const hostContext = app.getHostContext();96 const instanceId = hostContext?.toolInfo?.id ?? crypto.randomUUID();97 ```98 99 ### Broadcast and compare on a shared channel100 101 Broadcast the key and compare against every sibling you hear from. The comparison is `createdAt`, tie-broken by `seq`, then by instance ID for determinism. Ignore inbound messages until your own key is finalized so you never reply with an undefined key.102 103 ```ts theme={null}104 const channel = new BroadcastChannel("my-app-cart-supersede");105 const peers = new Map<string, { orderKey: number; seq?: number; instanceId: string }>();106 107 function isYounger(other: { orderKey: number; seq?: number; instanceId: string }) {108   // keyFinalized guards every call site, so orderKey is set by the time this runs.109   if (other.orderKey !== orderKey) return other.orderKey > orderKey!;110   if (other.seq != null && seq != null && other.seq !== seq) return other.seq > seq;111   return String(other.instanceId) > String(instanceId);112 }113 114 function recompute() {115   superseded = [...peers.values()].some(isYounger);116   render(); // defined in "Reflect the state in the UI" below117 }118 119 channel.onmessage = (ev) => {120   const msg = ev.data;121   if (!msg || msg.instanceId === instanceId) return;122   if (!keyFinalized) return;123   if (msg.type === "hello") {124     channel.postMessage({ type: "born", instanceId, orderKey, seq });125   }126   peers.set(msg.instanceId, msg);127   recompute();128 };129 130 function announce() {131   channel.postMessage({ type: "hello", instanceId, orderKey, seq });132   channel.postMessage({ type: "born", instanceId, orderKey, seq });133 }134 ```135 136 ### Gate host-mutating calls on `!superseded`137 138 The election only matters if superseded instances actually stop talking to Claude. Guard every call to [`updateModelContext`](https://modelcontextprotocol.github.io/ext-apps/api/classes/app.App.html#updatemodelcontext) or [`sendMessage`](https://modelcontextprotocol.github.io/ext-apps/api/classes/app.App.html#sendmessage):139 140 ```ts theme={null}141 // addButton, card, badge: elements in your widget's DOM.142 // pickRandomItem: your own helper that returns a string.143 144 function updateModelContext() {145   if (superseded) return;146   app.updateModelContext({147     content: [{ type: "text", text: `Cart has ${items.length} item(s): ${items.join(", ")}.` }],148   });149 }150 151 addButton.onclick = () => {152   if (superseded) return;153   items.push(pickRandomItem());154   render();155   updateModelContext();156 };157 ```158 159 ### Reflect the state in the UI160 161 In your render function, disable buttons and show a banner that points the user to the newest instance:162 163 ```ts theme={null}164 function render() {165   card.classList.toggle("superseded", superseded);166   badge.textContent = superseded ? "Superseded" : "Live";167   addButton.disabled = superseded;168 }169 ```170 171 ## Special considerations172 173 The election above covers the common case. A production widget should also handle the following.174 175 ### Channel scope and `ui.domain`176 177 `BroadcastChannel` is same-origin only. How far that origin extends depends on whether you set [`_meta.ui.domain`](https://modelcontextprotocol.github.io/ext-apps/api/interfaces/app.McpUiResourceMeta.html#domain) on your resource:178 179 * **Without `ui.domain`** (the default), Claude derives the iframe origin from the conversation and connector, so the broadcast is scoped to a single conversation.180 * **With a fixed `ui.domain`**, the origin is shared across every conversation and tab for your connector. A fixed channel name would let a widget in one conversation supersede a widget in another. Neither `hostContext` nor the tool-call arguments include a Claude-provided conversation ID, so if you need both a fixed domain and per-conversation elections, generate your own scope key on the server (for example, a UUID minted once per client connection) and return it in `structuredContent` for the widget to append to the channel name.181 182 ### Fall back if the server key is delayed183 184 The main snippet above waits for the `toolresult` event before announcing. If you want the widget to participate in the election even when that event is slow to arrive, replace that listener with one that resolves a promise, and race the promise against a short timeout after `connect()`:185 186 ```ts theme={null}187 let resolveServerKey!: (k: { orderKey: number; seq?: number }) => void;188 const serverKeyReady = new Promise<{ orderKey: number; seq?: number }>(189   (r) => (resolveServerKey = r),190 );191 192 // Replaces the toolresult listener from the first widget snippet.193 app.addEventListener("toolresult", (params) => {194   const sc = params.structuredContent as CartResult | undefined;195   if (sc?.items) items = sc.items;196   if (sc && Number.isFinite(sc.createdAt)) {197     resolveServerKey({ orderKey: sc.createdAt!, seq: sc.seq });198   }199 });200 201 // Place after the announce() definition in the broadcast snippet,202 // so channel is initialized before announce() runs.203 const serverKey = await Promise.race([204   serverKeyReady,205   new Promise<null>((r) => setTimeout(() => r(null), 1000)),206 ]);207 orderKey = serverKey?.orderKey ?? Date.now();208 seq = serverKey?.seq;209 keyFinalized = true;210 announce();211 ```212 213 If the server key arrives after the timeout, adopt it, recompute `superseded` against the peers you have already heard from, and re-announce so siblings update their view of you. The recomputed result may flip the instance back to live.214 215 ### Fallback caveat: don't compare server and client timestamps216 217 This applies only if you implemented the fallback above. If you fall back to a client-side `Date.now()` while waiting for the server key, tag the key with its source and refuse to compare a client value against a server value. A server `createdAt` from a tool call made hours ago will always be smaller than a fresh client timestamp, which would wrongly hand "live" to whichever instance happened to fall back. Include `keySource` in the broadcast payload (`announce()` and the `born` reply) and in the `peers` Map value type so siblings can read it:218 219 ```ts theme={null}220 type KeySource = "server" | "client";221 let keySource: KeySource = "client";222 223 function isYounger(other: { orderKey: number; seq?: number; instanceId: string; keySource: KeySource }) {224   if ((other.keySource === "server") !== (keySource === "server")) return false;225   // keyFinalized guards every call site, so orderKey is set by the time this runs.226   if (other.orderKey !== orderKey) return other.orderKey > orderKey!;227   if (other.seq != null && seq != null && other.seq !== seq) return other.seq > seq;228   return String(other.instanceId) > String(instanceId);229 }230 ```231 232 ### Caching the key across remounts233 234 On Claude.ai web, [`hostContext.toolInfo.id`](https://modelcontextprotocol.github.io/ext-apps/api/interfaces/app.McpUiHostContext.html#toolinfo) is the stable tool-use ID, so you can persist the resolved server key to `localStorage` keyed by that ID and reuse it on the next mount without waiting for the `toolresult` event again.235 236 Treat this as an optimization rather than a correctness guarantee. On Claude iOS, `toolInfo.id` is `undefined` when a stored conversation is rehydrated, so there is no stable per-instance cache key. Detect that case and skip the cache; the server key from the `toolresult` event is the only ordering source that works on every platform.237 238 ### If you bypass the SDK `App` class239 240 The snippets on this page use the SDK's [`App`](https://modelcontextprotocol.github.io/ext-apps/api/classes/app.App.html) class. If you instead hand-roll a minimal `postMessage` bridge, it will silently drop requests sent from the host to the widget, such as `ping` (a liveness check) and [`ui/resource-teardown`](https://apps.extensions.modelcontextprotocol.io/api/interfaces/app.McpUiResourceTeardownRequest.html) (the host asking the widget to clean up before unmount). Claude.ai web does not currently send either to widgets, and Claude iOS sends `ui/resource-teardown` only when the user navigates away from the conversation, so ignoring them is harmless today. The `App` class handles the full request surface and is recommended for production.241 242 ## Related topics243 244 * [Cross-platform compatibility](/docs/connectors/building/mcp-apps/cross-compatibility#domain-handling) for how `_meta.ui.domain` is computed on Claude.245 * [SDK API reference](https://modelcontextprotocol.github.io/ext-apps/api/index.html) for `registerAppTool`, `App`, and `McpUiResourceMeta`.
