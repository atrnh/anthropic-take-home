# Organizing cross-product documentation

The strongest default is a hybrid, task-first architecture:

- Organize shared concepts and common tasks by feature.
- Treat product and audience as independent metadata, not as mutually exclusive sections.
- Split into product-specific pages when procedures, prerequisites, terminology, or outcomes differ enough that a combined page becomes hard to follow.
- Give important content more than one route. A feature page can appear in both a product index and a task-based index without creating duplicate source content.

This is a starting hypothesis, not the answer. The exercises below help you test it.

## Why audience-first and product-first structures often struggle

Audience-based navigation sounds natural, but people often belong to multiple groups or need content written for another group. Nielsen Norman Group specifically warns that audience-based navigation can reduce usability when users span categories or need information aimed at several segments. GOV.UK similarly recommends against organizing API documentation by user type or experience level because users may not know which category describes them. [NN/g on audience-based navigation](https://www.nngroup.com/videos/audience-based-website-navigation/), [GOV.UK API documentation guidance](https://www.gov.uk/guidance/how-to-document-apis)

A pure product hierarchy has a related problem. Users who work with several products must repeatedly relearn the structure, and shared features tend to produce near-duplicate pages. Product names may also be irrelevant to someone who starts with a question such as "How do I manage access?"

The useful distinction is:

- **Tasks and features describe what the reader needs.**
- **Product identifies the context in which they need it.**
- **Audience affects prerequisites, framing, and permissions.**

The DITA standard models `product`, `audience`, and `platform` as separate applicability dimensions. You do not need to use DITA to borrow that idea. [OASIS DITA conditional-processing model](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/conditional-processing-attributes.html)

## Start with a feature-difference matrix

Before discussing menus, inventory the actual similarities and differences. Put documentation topics or user tasks in rows and products in columns.

Use a small set of relationship codes:

| Code | Meaning | Likely documentation treatment |
|---|---|---|
| `=` | Same concept and procedure | One shared page |
| `~` | Same procedure with small terminology or UI differences | Shared page with labeled notes |
| `⇄` | Same goal, materially different procedure | Shared overview with product-specific procedures |
| `U` | Unique to one or a few products | Product-specific page |
| `×` | Unsupported or unavailable | Availability statement or comparison table |

For each row, also record:

- The user’s goal
- Likely search terms
- Products to which it applies
- Audiences who perform the task
- Prerequisites and permissions
- Shared conceptual material
- Product-specific terminology
- Procedural differences
- Whether users compare products while doing this task
- Current page locations and owners

Do not turn the spreadsheet directly into navigation. Its job is to reveal the shape of the content.

Look for clusters:

- Many `=` and `~` cells suggest a shared feature section.
- Many `⇄` cells suggest shared feature overviews with product procedure pages.
- Mostly `U` cells suggest product-oriented documentation.
- Rows with substantial comparison behavior need a cross-product capability matrix.
- Rows used by several audiences should remain discoverable without requiring an audience choice.

## Map task overlap, not just audience overlap

Create one card for every important task. Ask representatives from each product’s user base to mark:

1. Which products they use for the task.
2. Whether they already know which product they need when they seek help.
3. Whether they move between products during the task.
4. What words they would search for.
5. What they expect to remain consistent across products.
6. What differences could cause a serious mistake.

Then combine the results into three sets:

- Tasks shared across products
- Tasks shared by some products
- Product-specific tasks

Analyze results by user group and across all groups. A Digital.gov IA project used this approach when it examined card-sort results separately for internal and external users while also looking for shared patterns. It found that moderated sessions were especially useful because participants explained ambiguous placements and identified missing content. [Digital.gov IA case study](https://digital.gov/2022/01/06/open-source-information-architecture-design-using-the-tools-you-have-to-conduct-card-sorting-and-tree-testing)

This exercise often exposes an important distinction: users may differ, but their documentation tasks may overlap heavily. If so, navigation by audience would exaggerate differences that do not matter to the task.

## Run a two-pass card sort

Use card sorting to generate possible groupings, not to approve a finished navigation tree. NN/g describes card sorting as a generative method for learning how users group and label information. It recommends tree testing for evaluating a proposed hierarchy. [NN/g card-sorting guidance](https://www.nngroup.com/articles/card-sorting-definition/)

### Pass 1: feature and task cards

Prepare representative cards such as:

- Configure access
- Add a team member
- Export audit events
- Set retention rules
- Troubleshoot failed synchronization
- Compare authentication options

Avoid putting product names on every card. Otherwise participants may merely produce product piles.

Ask each participant to:

- Group the cards.
- Name each group.
- Identify cards that belong in multiple groups.
- Leave unclear cards unsorted.
- Explain difficult placements.

### Pass 2: add product applicability

Give participants product markers and ask them to tag each card:

- Product A
- Product B
- Product C
- Multiple products
- Unsure

This separates two questions that a conventional card sort may blur:

- What belongs together?
- Which product context applies?

Run both passes with single-product users and multi-product users. Compare their results rather than averaging everything into one taxonomy. Strong differences between groups may justify alternate routes, but not necessarily separate content.

NN/g recommends roughly 30 to 50 cards for a substantial sort, but a smaller focused sort is reasonable when you are testing one feature family. Neutral card wording matters because repeated product or category terms can lead participants to group by matching words instead of meaning. [NN/g card preparation guidance](https://www.nngroup.com/articles/card-sorting-definition/), [NN/g on terminology bias](https://www.nngroup.com/articles/card-sorting-terminology-matches/)

## Prototype three competing structures

Do not workshop one hierarchy until everyone grows attached to it. Sketch at least these three:

### Candidate A: task-first

```text
Documentation
├── Manage access
│   ├── Overview
│   ├── Add members
│   ├── Configure roles
│   └── Troubleshoot access
├── Monitor activity
└── Manage data
```

Product differences appear within a task page or one level beneath it.

Use this when users begin with a goal and features behave similarly across products.

### Candidate B: product-first

```text
Documentation
├── Product A
│   ├── Manage access
│   ├── Monitor activity
│   └── Manage data
├── Product B
└── Product C
```

Use this when products have separate terminology, operating models, prerequisites, or user communities, and readers nearly always know their product first.

### Candidate C: hybrid with multiple routes

```text
Documentation
├── Features
│   ├── Manage access
│   ├── Monitor activity
│   └── Manage data
└── Products
    ├── Product A
    ├── Product B
    └── Product C
```

Both routes lead to canonical pages. The product pages are curated indexes, not duplicated documentation.

This is usually the best hypothesis when users overlap and features share a recognizable model. Polyhierarchy, allowing one item to have more than one parent, supports differing mental models. Use it selectively because listing every topic everywhere makes menus harder to scan. [NN/g on polyhierarchy](https://www.nngroup.com/articles/polyhierarchy/)

## Tree-test the candidate structures

Give users realistic prompts and a plain-text hierarchy. Remove page design, search, and visual hints so you are testing category structure and labels.

Useful tasks include:

- "You use Product B and need to change who can approve requests. Where would you look?"
- "You are evaluating several products and want to know which support audit exports."
- "You know how retention works in Product A. Find out whether Product C works the same way."
- "A Product A procedure failed. Find troubleshooting information."
- "You administer Product A but need instructions intended for an end user."

Measure:

- Success rate
- First choice
- Final destination
- Directness
- Backtracking
- Time to destination
- Confidence
- Places participants expected the content to appear

First run a few moderated sessions. Fix confusing prompts and ask why participants chose each branch. Then, if needed, run a larger unmoderated comparison. NN/g recommends this sequence because qualitative testing exposes unclear labels and task bias before quantitative measurement. Tree testing can compare several candidate hierarchies before you build page layouts. [NN/g tree-testing guidance](https://www.nngroup.com/articles/tree-testing/)

Pay special attention to wrong-product errors. Finding a plausible page for the wrong product is often more dangerous than failing to find a page at all.

## Test how product differences appear on a page

Navigation research will not tell you whether differences should appear as callouts, tabs, separate sections, or separate pages. Prototype the same topic in several forms.

### Inline differences

```text
To enable exports, open Settings > Data.

Product C: An organization owner must enable exports before
workspace administrators can use this setting.
```

Use when most of the page is shared and differences are short.

### Product sections

```text
## Product A

...

## Product B

...
```

Use when readers need to compare products or when all variants should be searchable and visible.

### Product selector

```text
[Product A] [Product B] [Product C]
```

Use when the variants follow the same task structure but differ enough that showing all of them creates noise.

Make the selection visible, persistent, and part of the URL. Readers should be able to share a link that opens the correct product context. GitHub’s documentation does this for versions and tool-specific content. Its guidance also limits switchers to cases where the task or concept changes, recommends using as few options as possible, and supports links that preserve the selected option. [GitHub versioning model](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation), [GitHub tool-switcher guidance](https://docs.github.com/en/contributing/writing-for-github-docs/creating-tool-switchers-in-articles)

A selector is a poor fit for dozens of products. At that scale, use a product index, search filter, comparison table, or separate variant pages.

### Separate pages

Use separate pages when:

- Steps have little meaningful overlap.
- Products use different terminology or conceptual models.
- Permissions and prerequisites differ substantially.
- Combining variants creates extensive conditional prose.
- A reader could accidentally follow the wrong procedure.
- Each variant needs its own lifecycle or owner.

Link the pages as equivalents so users can move from "Configure access for Product A" to the corresponding Product B page.

During testing, ask participants to state:

- Which product the instructions apply to
- Whether the task is supported in another product
- What differs between products
- Where they would switch context
- Which link they would share with a colleague

## Run a cross-product switching test

Most documentation tests begin at the home page. That misses the behavior you care about.

Start participants deep inside a product-specific page and ask them to:

1. Find the equivalent information for another product.
2. Return to the original product.
3. Compare the two.
4. Share the second page.
5. Explain which context is active.

This tests whether product context is understandable outside the navigation path. That matters because users often arrive through search, bookmarks, support tickets, or shared links.

Every page should make the following obvious without relying on breadcrumb history:

- Current feature or task
- Applicable product
- Applicable version, plan, or platform when relevant
- Audience or permission prerequisite
- Availability in related products
- Route to equivalent information

## Simulate a product change

IA can test well and still become expensive or inaccurate after six months. Run a maintenance exercise before committing to it.

Choose one scenario:

- Add a new product that supports half of the existing features.
- Rename a shared feature in one product.
- Change one product’s procedure while preserving the others.
- Retire a feature from one product.
- Move a capability from one plan to another.

Ask the documentation team to identify every page, navigation item, include, condition, comparison table, and search label that would need to change.

Record:

- Number of source locations touched
- Whether the canonical source is obvious
- Risk of leaving contradictory copies
- Reviewers needed
- Whether all rendered product variants can be previewed
- Whether old links remain valid

GitHub uses single-source pages, explicit applicability metadata, reusable content, and conditional rendering to reduce duplication. Its guidance also warns that conditional logic becomes difficult to understand when it grows too implicit or complicated. When the conditional prose becomes harder to maintain than separate passages, repetition can be the safer choice. [GitHub versioning guidance](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation), [GitHub reusable-content guidance](https://docs.github.com/en/contributing/writing-for-github-docs/creating-reusable-content)

The principle is "reuse stable meaning," not "deduplicate every sentence."

## Recommended pattern library

| Pattern | Best fit | Main risk |
|---|---|---|
| Shared task page | Concept and procedure are substantially the same | Small differences become easy to miss |
| Shared page with product callouts | Differences are short and exceptional | Too many callouts fragment the procedure |
| Shared overview with product procedure pages | Same goal, different execution | Readers may land on the overview and miss the procedure |
| Product selector | Same page structure, several meaningful variants | Hidden context and poor scaling |
| Product portal | Products have distinct models and users usually know their product | Duplication and siloed discovery |
| Faceted feature index | Users compare products or do not yet know which product fits | Filters can become a second, complicated navigation system |
| Capability matrix | Availability and differences drive product selection | A large matrix can become difficult to scan and maintain |
| Polyhierarchical placement | A topic has several plausible homes | Navigation inflation |
| Related-product links | Equivalent topics already live on separate pages | Links drift unless relationships are stored as metadata |

## A practical decision rule

For each feature, ask these questions in order:

1. Can one title describe the reader’s goal across products?
2. Is the underlying concept the same?
3. Can one procedure remain accurate without frequent product conditions?
4. Would showing every product variant help, or distract, the reader?
5. Could following the wrong variant cause harm or irreversible work?
6. Do readers need to compare products?
7. Do readers often move between products during the task?

Then choose:

- Same goal, concept, and procedure: one page.
- Same goal with small differences: one page with explicit product notes.
- Same goal with different procedures: shared overview plus product-specific procedures.
- Different concepts or materially different outcomes: separate product pages.
- Frequent comparison: add a capability matrix or side-by-side comparison.
- Several plausible entry routes: cross-list the canonical page.
- Many variants: avoid a giant tab set.

## What I would test first

A focused first round can be modest:

1. Build the feature-difference matrix for the 20 to 30 most important tasks.
2. Interview a few single-product and multi-product users about where they begin.
3. Run an open card sort using task-focused labels.
4. Sketch task-first, product-first, and hybrid trees.
5. Tree-test all three with the same realistic tasks.
6. Prototype one high-overlap page and one high-divergence page.
7. Run the cross-product switching test.
8. Use the results to set page-splitting and product-selector rules.

My initial hypothesis would be the hybrid structure: task and feature pages as the canonical content, product pages as curated entry points, explicit product applicability on every page, and separate procedures where the products genuinely diverge.

Also preserve multiple ways to find the same information. Hierarchical navigation alone will not fit every user. Search, breadcrumbs, related links, product indexes, and feature indexes support different navigation strategies and are consistent with WCAG guidance. [W3C Understanding WCAG 2.4.5, Multiple Ways](https://www.w3.org/WAI/WCAG22/Understanding/multiple-ways)
