Also distinguish an explicit source statement from an extractor’s inference. A field supported by the page title or surrounding section can be marked as inherited scope; a guessed product mapping should remain unresolved.

**Capture enough procedure to compare it**

A procedure summary should preserve the distinctions that could change the documentation treatment:

- Who initiates it.
- Where they perform it.
- What they provide or select.
- The meaningful sequence and decision points.
- Whether another actor must approve or complete something.
- Whether the result applies personally, to a workspace, or to an organization.
- Any explicit platform-specific steps.

“Install through settings” loses too much. Copying every sentence creates unnecessary reading for the comparison stage. Capture the meaningful steps and retain a pointer to the full procedure. Preserve exact UI labels when they are relevant to the comparison.

**An example from the Government page**

The [Government administration page](~/personal/anthropic-take-home/corpus/government/config/plugins-and-connectors.md) could produce an observation like this:

| Field | Extracted observation |
|---|---|
| Candidate task | Provide members with a connector |
| Source terminology | “Plugins” card; “Connectors” card |
| Product context | Claude for Government |
| Actor | Tenant administrators and organization owners, as declared by the page |
| Mechanism | Connectors are delivered through the Connectors card |
| Explicit exclusion | A connector declared in a plugin uploaded through the Plugins card is not connected |
| Procedure coverage | This page identifies the delivery route and links to further connector instructions |
| Evidence location | “Plugins versus connectors” section |
| Supporting excerpt | “to give members a connector, add it on the **Connectors** card instead” |

That observation preserves an actionable distinction without claiming the page provides the entire connector setup procedure.

**Keep these judgments for the comparison stage**

I would not ask source extractors to assign:

- `=`, `~`, or `⇄`.
- “Unique to this product.”
- Shared-page versus separate-page recommendations.
- Whether two differently named tasks are definitively equivalent.
- Whether users frequently switch between or compare products.

Those require evidence across sources, or user research. Extractors can propose task matches and flag possible differences, but those proposals should remain separate from source-backed facts.

Likewise, **absence belongs in the coverage record**. An extractor can report “this page does not describe authentication prerequisites.” It cannot conclude “the product has no authentication prerequisites.”

The minimum useful extraction is therefore **a scoped task, its documented behavior, its qualifications, and supporting evidence**. Everything else should help compare those observations or expose what we still need to learn.

## ChatGPT

The skill has a useful structure: bounded extraction, saved records, per-task reconciliation, and deterministic rendering. I would keep that structure. **I would revise the data model and gap rules before the full run**, because the pilot shows cases where the pipeline turns incomplete documentation into an apparent product difference.

I agree with the diagnosis that the product axis mixes categories. I only partly agree with the proposed fix.

**`admin-console` is a surface, but it is not a product**

An administrator is an actor. An admin console is where that actor works. Neither tells us which product or deployment the procedure affects.

The current taxonomy groups Claude organization settings, the Government admin portal, and Slack administration under one `admin-console` product. That loses precisely the context we want to compare.

I would separate these dimensions:

| Dimension | Question it answers | Example |
|---|---|---|
| Product context | Which product or deployment does this task concern? | Claude for Government |
| Actor | Who performs it? | Organization administrator |
| Interaction surface | Where do they perform it? | Government admin portal, Plugins card |
| Mechanism | How do they perform it? | UI |
| Outcome | What does completing it accomplish? | Makes a plugin available to members |

So I agree with removing `admin-console` as a product column, but **preserve the actual administration surface**. Folding it into `actor: admin` alone discards useful procedural information.

The same issue appears in the [mechanism definitions](~/personal/anthropic-take-home/.claude/skills/task-matrix/references/schema.md:15): `ui` and `admin-console` overlap. An admin console can be a UI, and an administrator can also use a CLI or configuration file. Separating these fields would make family assignment more consistent.

**I would also remove `developer-platform` as currently defined**

It describes a collection of developer activities, not one identified platform. Building a server, testing an MCP App in Desktop, and submitting a directory listing have different destinations and outcomes.

I would retain developer tasks in the dataset and give them their own view:

- A product comparison view for tasks with meaningful product variants.
- A builder and publisher task inventory for shared development and publication workflows.
- Product-specific developer comparisons where the sources establish them.

This does not require separate extraction pipelines. It requires an explicit comparison scope for each task.

I would not encode “developer-platform applies only to T-051 through T-069.” That ties meaning to the current numbering and already misses **T-041, submit a plugin to the plugin directory**. Conversely, T-064 explicitly concerns testing an MCP App in Claude Desktop. Developer tasks can have a real product context.

Also, the pilot’s claim that “extraction records do not change” is too optimistic. Records currently assigned to `admin-console` have lost their product context. Some can be remapped from their source; others need targeted rereading. Removing the column and rerunning merge cannot recover that information by itself.

**The gap logic needs an independent fix**

In [merge.py](~/personal/anthropic-take-home/.claude/skills/task-matrix/scripts/merge.py:14), every product observed anywhere becomes part of every task’s comparison scope. The [reconciler](~/personal/anthropic-take-home/.claude/skills/task-matrix/references/reconcile-prompt.md:21) then labels every product without a record `absent`.

That creates noise even with a perfect product taxonomy. It also means a product with no extracted procedures disappears from the comparison altogether.

I would distinguish:

| State | What we know |
|---|---|
| Procedure documented | The source explains how to complete the task |
| Partial procedure or pointer | The source describes a stage or refers elsewhere |
| Availability documented, procedure missing | The source establishes applicability without instructions |
| Explicitly unsupported | The source rules out the task under stated conditions |
| Not established in reviewed material | The available evidence does not answer the question |
| Outside comparison scope | This task/product pairing is excluded for a recorded reason |

A documentation gap should be a conclusion supported by applicability and coverage. It should not be the default value of an empty cell. For a pilot covering 11 of 54 pages, the missing-data language also needs to say “in the pilot material.”

**The most consequential pilot error is task matching**

The [T-033 result](~/personal/anthropic-take-home/docs/1-audit/task-matrix/pilot/matrix/T-033.json) treats this as a variant of *install a plugin*:

> Open the plugin directory; alternatively, use Plugin Create to build your own.

The record itself acknowledges that the source never documents installation. Nevertheless, the matrix marks the task documented and assigns `mechanism-differs` and `steps-differ`.

That is a difference in **what the pages explain**, not established evidence of a different installation procedure.

The taxonomy helped cause this: “browse plugins” is an alias of “install a plugin.” Browsing and installing are related tasks, but completing one does not complete the other.

I would tighten matching around the outcome:

> Does following this procedure accomplish the task named by the row?

If not, record it as a prerequisite, partial procedure, related task, or pointer. Do not treat it as a complete variant.

This matters more than achieving zero `NEW` candidates. The extraction prompt’s preference for an existing ID “when the fit is close” encourages forced matches.

**The procedure-only scope is too narrow for the original matrix**

The [schema](~/personal/anthropic-take-home/.claude/skills/task-matrix/references/schema.md:71) explicitly excludes conceptual descriptions and non-actionable reference material. That is defensible for a procedure inventory, but a feature-difference matrix also needs availability, restrictions, and behavioral differences.

I would add a small supporting observation type for:

- Availability and explicit exclusions.
- Preconditions and limits.
- Behavior or outcomes that distinguish products.

These observations would support task comparisons without requiring invented steps. The Government rule about connectors in uploaded plugins is a good example of information that must survive even when it appears outside a procedure.

**Context isolation currently goes too far**

Both workers and reconcilers have strict reading boundaries. The reconciler is explicitly forbidden from reading corpus pages. Meanwhile, the splitter puts the page preamble in a separate unit; later units receive headings but not necessarily the scope and qualifications stated in that preamble.

That can leave a worker without relevant conditions and prevent the reconciler from recovering them.

I would retain bounded assignments but allow:

- Page-level scope and prerequisite context in every chunk.
- Targeted source reads during reconciliation.
- A recorded unresolved question when the necessary source falls outside the corpus.

This preserves context discipline while allowing evidence checks. Forbidding source access makes extraction loss permanent.

**The validation and QA are useful, but their claims need narrowing**

A matching quote proves that a passage exists. It does not prove all the extracted steps, conditions, or product assignments. The current validator also checks product-evidence wording without checking that the product-evidence string occurs in the source.

Two implementation issues deserve attention before scaling:

- [Validation](~/personal/anthropic-take-home/.claude/skills/task-matrix/scripts/validate.py:64) can exit successfully despite missing extractions or rejected records.
- Merge reads every file in `accepted/`; old accepted files can survive a failed or changed rerun and enter the result.

Use the current unit manifest and validation report to determine what is eligible for merging, and require explicit accounting for incomplete units.

The independent re-extraction is a good start, but agreement on task IDs and mechanisms measures consistency. It does not establish that both workers retained the right conditions or avoided the same taxonomy mistake. The plugin-install example should become a reviewed QA case.

There is also a reporting discrepancy: the [pilot README](~/personal/anthropic-take-home/docs/1-audit/task-matrix/pilot/README.md) says the plugin overview came back empty, while its saved extraction contains the installation record described above. I would reconcile that before relying on the pilot’s success claims.

**My recommendation**

Keep the pipeline and run a focused second pilot after these changes:

1. Separate product context, actor, interaction surface, and mechanism.
2. Define task comparison scope explicitly; remove blanket `absent` classification.
3. Require task-outcome matching and distinguish partial instructions from complete procedures.
4. Preserve non-procedural restrictions and allow targeted source rereads.
5. Make validation and merge account for missing, rejected, and stale records.

Reuse valid pilot evidence and revisit the affected records. There is no need to discard the work. The pilot has exposed useful problems, but the next run should test whether the matrix distinguishes **product differences, documentation differences, and uncertainty**. Right now those three still blur together.
