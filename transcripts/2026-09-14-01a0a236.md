## ChatGPT

The existing task matrix reproduces the problem: its “product” columns mix Claude, Cowork, Government, and third-party inference. Renaming that column “surface” would still mix different things. The useful comparison is a task and its procedures, with explicit conditions for where each procedure applies.

## ChatGPT

I recommend **organizing the slice around shared capabilities and reader tasks, with explicit context for the differences**.

The core model would be:

> Claude uses connectors to access tools and data, skills to follow reusable instructions, and plugins to package capabilities for distribution. How you enable, use, or administer them depends on where you use Claude and how your organization provides access.

That gives us a stable conceptual foundation without implying that every capability works everywhere.

## 1. What is wrong with the current hierarchy?

The landing page puts several different kinds of things under “All products”:

| Current entry | What it represents for documentation |
|---|---|
| Connectors, skills, plugins | Shared capabilities and their packaging |
| Cowork | A way of working within Claude Desktop |
| Claude Tag | Claude working in Slack, including shared-channel behavior |
| Claude for M365 | Claude inside several Microsoft 365 applications |
| Claude Science | A specialized research application and working environment |
| Claude on third-party platforms | A deployment and inference arrangement |
| Claude for Government | An offering with distinct administration and deployment constraints |

The landing page treats these as peers, although a reader can encounter several simultaneously. Someone might use a **plugin**, in **Cowork**, in **Claude Desktop**, under a particular **deployment arrangement**. [Current docs landing page](https://claude.com/docs)

One precision matters here: Cowork is within Claude Desktop; it is not synonymous with the whole application. Science is documented as a desktop application of its own. We should preserve those distinctions while explaining shared concepts once. [Cowork overview](https://claude.com/docs/cowork/overview), [Claude Science overview](https://claude.com/docs/claude-science/overview)

We do not need to settle Anthropic’s commercial definition of “product” to fix this. We need categories that help readers locate the right explanation and procedure.

## 2. The conceptual model

Separate **what the thing is**, **what the reader wants to accomplish**, and **the conditions under which the instructions apply**.

| Dimension | Question it answers | Examples |
|---|---|---|
| Capability or artifact | What am I working with? | Connector, skill, plugin |
| Task | What outcome do I need? | Connect a service, import a skill, distribute a plugin |
| Place of use | Where will Claude use it? | Cowork in Desktop, Slack channel, Word, Science |
| Access and deployment | How is Claude provided here? | Direct Claude account, third-party inference, Government environment |
| Actor and scope | Who is doing this, and whom does it affect? | Member, organization owner, tenant administrator; personal, channel, organization |
| Mechanism | How does the task happen? | Upload, GitHub sync, managed configuration |

These are independent dimensions. A web admin console is **where an administrator performs a step**; Slack may be **where the resulting capability becomes available**. Both facts matter, and calling both “surface” obscures the distinction.

Also, connectors, skills, and plugins have a relationship, rather than being three interchangeable extension types:

- A connector supplies access to tools and data.
- A skill supplies instructions and resources for doing a task.
- A plugin packages capabilities, potentially including skills and connectors.

That relationship is already described in the [pinned plugin overview](~/personal/anthropic-take-home/corpus/plugins/overview.md). Documenting it centrally would make the rest of the slice easier to understand.

## 3. Proposed reader-facing navigation

I would use this structure for the slice:

```text
Extend Claude
├── Understand connectors, skills, and plugins
├── Connectors
│   ├── Find and connect a service
│   ├── Use connected tools and data
│   ├── Manage access
│   └── Troubleshoot
├── Skills
│   ├── Find and use skills
│   ├── Add or import a skill

├── Plugins
│   ├── Find and install plugins

├── Administer extensions

│   └── Update and remove managed extensions
└── Build and publish extensions
    ├── Build connectors and MCP Apps
    ├── Package extensions
    └── Submit and maintain directory listings
```

Alongside that capability-and-task navigation, retain **“Where you use Claude”** entry points for Cowork, Slack, M365, and Science, and **“Deploy and administer Claude”** entry points for deployment-specific guidance.

These should lead to the relevant shared documentation and specialized procedures. They should not each recreate their own complete connectors/skills/plugins manual.

For example, someone entering through “Claude in Microsoft 365” should find “Use skills in Word” easily. Someone entering through “Skills” should reach the same instructions.

**One canonical home for a procedure, multiple useful routes to it.**

## 4. What to consolidate, and what to preserve

The rule should be:

> Share the explanation when the concept is the same. Share the procedure when the actor, steps, and outcome are the same. Keep a separate procedure when the differences change what the reader must do.

The corpus gives us concrete examples:

| Source | Proposed treatment |
|---|---|
| [M365 connectors and skills](~/personal/anthropic-take-home/corpus/office-agents/connectors-and-skills.md) | Link to shared definitions. Keep M365 instructions for the connector menu and skill picker, plus the connection-mode availability condition. |
| [Personal connectors in Slack channels](~/personal/anthropic-take-home/corpus/claude-tag/concepts/personal-connectors.md) | Keep a dedicated procedure. Requester identity, channel visibility, and review-before-posting materially change the task. |
| [Science connectors and skills](~/personal/anthropic-take-home/corpus/claude-science/connectors-and-skills.md) | Reuse definitions; retain featured connector behavior, scientific resources, and Science-specific controls. |
| [Government plugin administration](~/personal/anthropic-take-home/corpus/government/config/plugins-and-connectors.md) | Keep specialized distribution instructions and package restrictions. This path does not connect connectors declared inside an uploaded plugin. |
| [Built-in connectors under third-party inference](~/personal/anthropic-take-home/corpus/third-party/claude-desktop/built-in-connectors.md) | Keep managed-configuration instructions. These servers run locally and are activated by administrators. |

This avoids turning every page into a long list of exceptions. A short difference can live beside a shared procedure. A different access model or substantially different workflow deserves a linked page with a specific title.

It also keeps **the Microsoft 365 connector** distinct from **Claude inside Microsoft 365 apps**. One provides access to a service’s data; the other describes where the person works with Claude. The M365 overview explicitly describes a set of add-ins. [Claude for M365 overview](https://claude.com/docs/office-agents/overview)

## 5. How this unblocks the task matrix

The [current pilot inventory](~/personal/anthropic-take-home/docs/1-audit/task-matrix/pilot/out/inventory.md) still uses “products” as its columns. Those columns mix an application, a working mode, a deployment arrangement, and an offering.

**I would remove `product` as the organizing axis, rather than rename it `surface`.**

The primary inventory should be:

| Task | Procedure | Applies when | Actor | Meaningful difference | Evidence |
|---|---|---|---|---|---|

Keep task IDs and source-backed procedure records. Describe applicability using only the dimensions the source actually establishes.

For example:

- **Task:** Make a plugin available to a group.
- **Government procedure:** Upload through the admin portal and choose install behavior.
- **Slack procedure:** Upload or sync the plugin, then attach it to a scope.
- **Shared concept:** Distributing a plugin.
- **Distinct instructions:** Delivery mechanism, target scope, and activation.

We can still generate comparison tables for a specific question, such as “How does plugin installation differ across working environments?” But that table is a view of the evidence, not the underlying taxonomy.

Two evidence rules are essential:

1. A generic page does not prove that its procedure applies everywhere.
2. A missing procedure in this 54-page slice means **not documented in the slice**, not **unsupported**.

## Recommended next step

Apply this model first to **plugin installation and distribution**. That gives us a bounded comparison across Cowork, Government, and Claude Tag, with both common concepts and substantial procedural differences.

Use that comparison to validate the revised inventory structure before rerunning the full corpus extraction. Preserve the pinned corpus as evidence; proposed page moves, rewrites, and redirects belong in the audit deliverables.

I have left the files unchanged. This proposal is grounded in the live landing and overview pages, the existing pilot, and representative corpus pages; it is not yet a complete page-by-page migration map.
