## ChatGPT

The key change is that we should separate **candidate generation** from **editorial judgment**. The original checker tried to make one lexical similarity metric do both jobs, which is why it behaved badly.

A better architecture would look roughly like this:

1. **Deterministic preprocessing.** Parse the Markdown corpus into meaningful chunks—probably paragraph/section-sized explanatory passages rather than arbitrary windows. Keep metadata such as file, heading hierarchy, line numbers, and perhaps the preceding/following paragraph. Continue excluding things we know aren't relevant, like code blocks, tables, nav cards, and procedures if the audit is specifically about duplicated explanatory prose.

2. **Generate plausible candidates cheaply.** We don't want to send every possible pair of passages to an LLM. With 1,000 passages, that's ~500,000 comparisons. Embeddings are well suited to this stage: embed each passage, retrieve its nearest semantic neighbors, and only consider pairs above a deliberately permissive similarity threshold. Unlike the current trigram approach, embeddings can retrieve paraphrases. This embeddings → candidate pairs pattern is a standard semantic-deduplication technique. citeturn0search1turn0search6

3. **Have the LLM make the actual editorial judgment.** Importantly, I wouldn't ask simply, *“Are these passages duplicates?”* I'd encode the standard we're actually trying to enforce. Something more like:

   > Do these passages perform substantially the same explanatory function? If so, could one be removed, shortened, or replaced with a cross-reference **without making either page less understandable or its procedure less independently usable?**

   And force a structured result such as `ACTIONABLE_DUPLICATE`, `NECESSARY_REPETITION`, or `RELATED_BUT_DISTINCT`, plus the shared explanation, unique information in A/B, and a suggested consolidation.

That distinction is exactly what killed the deterministic version. The Gmail prerequisite might be extremely semantically similar but should come back `NECESSARY_REPETITION`. Two differently worded explanations of what a plugin does might have lower lexical overlap but come back `ACTIONABLE_DUPLICATE`.

There's actually a very close precedent for this architecture in NVIDIA's SkillEvaluator: its intra-skill redundancy check uses embeddings to identify candidate clusters and then an LLM to distinguish actual duplicates from intentional detail and related-but-distinct content. citeturn0search0

The rest of the system can remain deterministic. Code can verify that the reported files and line ranges exist, ensure the model's quoted evidence is actually present in those passages, validate the output schema, deduplicate findings, and produce the report. So the model is responsible only for the part that genuinely requires semantic/editorial reasoning.

For this take-home specifically, I'd also make the **evaluation methodology a prominent part of the deliverable**. We already have a particularly useful test set because the failed implementation gave us adversarial examples:

- known unnecessary explanatory duplication, including paraphrases;
- repeated prerequisites that *must* remain local;
- same vocabulary used for different purposes;
- overview → detail repetition that represents legitimate progressive disclosure.

Then compare:

**lexical baseline → embedding retrieval → embedding + LLM judgment**

against the independently labeled examples. That gives us a much more interesting result than simply saying, "I made an AI linter." We can demonstrate *why* semantic judgment is needed and quantify whether adding it actually improves precision/recall.

I also wouldn't necessarily throw away the current implementation. I'd demote it to **`baseline`**. Its terrible result—3/18 useful findings and 0/6 known duplicates recovered—is valuable experimental evidence. The story becomes:

> We hypothesized that lexical similarity could detect duplicated explanatory prose. Evaluation falsified that hypothesis: lexical overlap conflates necessary repetition with redundant explanation and misses paraphrases. We therefore retained lexical matching as a baseline and tested a semantic candidate-retrieval + model-judgment architecture.

That's a considerably stronger engineering narrative than quietly replacing the first approach after it performed poorly. It shows that the checker was designed around measured failure modes rather than around whichever technique sounded sophisticated.

## ChatGPT

Yes. For a take-home-sized corpus, this can be very cheap—potentially effectively free—and you don't need a vector database or any infrastructure.

The simplest implementation I'd use is:

```text
Markdown corpus
    ↓
extract explanatory passages
    ↓
embed each passage once
    ↓
cosine similarity
    ↓
top semantic neighbors / threshold
    ↓
small candidate set
    ↓
LLM judges actual redundancy
```

For only 54 pages, you can just keep all embeddings in memory and use NumPy cosine similarity. No Pinecone, FAISS, database, server, etc. Even a few thousand passages is trivial.

For embeddings, there are two sensible options.

**Option A: local embeddings — $0.** Use `sentence-transformers` with a small model such as `all-MiniLM-L6-v2`. It downloads once and runs locally:

```python
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

model = SentenceTransformer("all-MiniLM-L6-v2")

embeddings = model.encode(
    [passage.text for passage in passages],
    normalize_embeddings=True,
)

similarities = cosine_similarity(embeddings)
```

That is probably sufficient for this experiment. We're not building production semantic search; we're deliberately doing **high-recall candidate generation**. The LLM handles the difficult judgment afterward.

**Option B: a hosted embedding API.** Also extremely inexpensive at this scale. You embed every passage once, cache the vectors in a JSON/NumPy file, and subsequent runs only embed passages whose content hash changed. The actual cost for a documentation corpus of this size should be tiny.

There's also an important optimization: **don't ask the LLM to examine every pair above some broad threshold.** For each passage, take perhaps its 3–5 nearest neighbors, discard same-section/self matches and anything below a permissive similarity floor, normalize `(A, B)` so duplicates collapse, then send that shortlist to the judge.

Suppose extraction gives us 800 passages. Exhaustively comparing them gives:

\[
{800 \choose 2} = 319{,}600
\]

pairwise comparisons. But those cosine calculations are basically free locally. If we retrieve only the top 3 neighbors per passage, we'd have at most ~2,400 pairs before deduplication—and probably dramatically fewer after a similarity cutoff. Maybe only tens or low hundreds need an LLM call.

I actually think **local MiniLM + an LLM judge** is especially appropriate for the assignment. It gives the architecture a clean division of labor:

> Embeddings are used only as a high-recall retrieval mechanism. They identify semantically similar passages cheaply; they do not determine whether duplication is editorially inappropriate. A model evaluates the smaller candidate set against the documentation standard.

And we can test whether MiniLM is good enough rather than assuming it. Take the six known duplicates we already labeled and ask: **does each duplicate appear among the other passage's top-k semantic neighbors?**

That's a straightforward retrieval metric—`Recall@k`. If all six appear in the top 5 or top 10, great. If MiniLM only finds 4/6, we know candidate generation itself needs improvement before even evaluating the judge.

So I'd probably modify the prototype into something like:

```text
docslint/
    duplicates.py          # existing lexical baseline
    semantic_duplicates.py # embeddings + candidate retrieval
    judge_duplicates.py    # LLM editorial classification

docs/3-check/
    examples.json          # existing independent labels
    baseline-results.json
    semantic-results.json
    README.md
```

Then the README can report retrieval recall separately from **end-to-end precision/recall**. That makes the experiment much more rigorous while keeping the implementation surprisingly small.

One caveat: `sentence-transformers` adds a fairly substantial PyTorch dependency. If this repo is intended to be cloned and run easily by Anthropic reviewers, I'd consider whether a hosted embeddings API with one lightweight SDK dependency is actually the cleaner implementation despite costing a few cents. That's probably the main tradeoff I'd investigate before choosing.

## ChatGPT

Yes. I think the useful abstraction is not “embeddings”; it's **cheap, high-recall semantic-ish retrieval**. We only need something good enough to reduce the search space before the LLM does the real reasoning.

There are several lightweight approaches that avoid PyTorch entirely.

The one I'd be most interested in is **TF-IDF + cosine similarity**. `scikit-learn` gives you this out of the box:

```python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

vectorizer = TfidfVectorizer(
    ngram_range=(1, 2),
    stop_words="english",
    sublinear_tf=True,
)

vectors = vectorizer.fit_transform(passages)
similarity = cosine_similarity(vectors)
```

That's conceptually similar to embeddings—represent passages as vectors, retrieve nearest neighbors—but the vectors encode lexical importance rather than learned semantics. It should outperform the current trigram-overlap detector on passages that express the same concept with moderately different wording, while remaining deterministic, local, fast, and boring.

And “boring” is useful here.

There are a few other possibilities:

- **BM25 retrieval.** Treat each passage as a tiny document and query every passage against the others. Lightweight and excellent lexical retrieval, though probably not dramatically better than a good TF-IDF setup for this corpus.
- **Character n-grams.** Surprisingly useful for detecting rewritten/copied prose because they tolerate small wording changes. TF-IDF over character 3–5 grams could be combined with word TF-IDF.
- **MinHash/LSH.** Very cheap and scalable for near-duplicate detection, but it's mostly solving the problem we already discovered isn't enough: lexical duplication rather than semantic redundancy.
- **Keyword/concept extraction with the LLM.** Ask the model once per passage to produce something like `["plugin definition", "MCP relationship", "installation behavior"]`, then deterministically compare those labels. Interesting, but now we've simply moved the model call earlier in the pipeline.
- **Let the LLM generate candidates directly.** This is the genuinely radical alternative.

That last one deserves consideration because **54 pages is tiny**.

Instead of constructing a sophisticated retrieval system, we could organize the documentation into batches and ask the model:

> Identify explanations in these sections that appear to substantially overlap explanations elsewhere in this batch. Ignore repeated prerequisites, procedural steps, warnings, and other information that readers need locally.

Then do a second pass that compares candidates across batches.

There are variants of this where you first have the model create a compact **explanation inventory**:

```text
connectors/overview.md
  - What connectors are
  - Relationship between connectors and MCP
  - Authentication responsibilities
  - Remote vs local connectors

plugins/overview.md
  - What plugins are
  - How plugins differ from connectors
  - Plugin distribution model
```

Now finding duplication becomes dramatically easier: compare the *inventory entries*, not every paragraph against every other paragraph.

I actually like that approach for this particular audit because it attacks the problem at the correct conceptual level.

The audit finding isn't really:

> “Some paragraphs have high semantic similarity.”

It's:

> “The documentation **explains the same concept in multiple places** rather than establishing a canonical explanation and referring readers to it.”

So the object we want to detect may not be a *similar passage* at all. It may be a **repeated explanatory responsibility**.

For example:

```text
Page A
"What is a plugin?"
    ↓
explanatory responsibility:
PLUGIN_DEFINITION

Page B
"Understanding plugins"
    ↓
explanatory responsibility:
PLUGIN_DEFINITION

Page C
"Install a plugin"
    ↓
prerequisite:
PLUGIN_ACCESS_REQUIREMENT
```

A model can identify those responsibilities much more naturally than an embedding model can decide editorial redundancy.

That suggests a pipeline like:

```text
54 Markdown pages
        │
        ▼
 deterministic extraction
        │
        ▼
 LLM: inventory explanatory concepts
        │
        ▼
 normalize / group concept labels
        │
        ▼
 candidate repeated explanations
        │
        ▼
 LLM: editorial judgment
        │
        ▼
 source/evidence validation
```

This has another nice property: **the intermediate representation is inspectable by an editor.** Instead of saying “cosine similarity = .83,” the report can say:

> These three passages were classified as explaining **how plugins relate to connectors**.

Then show the passages and ask whether one should become canonical.

That seems substantially more aligned with the task.

If cost is the concern, batching makes this potentially quite cheap. We're talking about 54 documentation pages, not millions of documents. We can cache every model-produced inventory keyed by the source content hash, so unchanged pages never need to be analyzed again.

And importantly, we already have the perfect way to decide among these approaches rather than theorizing about them. We have the labeled examples.

I'd run a tiny bake-off:

```text
Current trigram baseline
        vs.
TF-IDF top-k retrieval
        vs.
LLM explanation inventory
```

The first question isn't even end-to-end accuracy. It's simply:

**Of our six known cases of unnecessary explanatory duplication, how many does each approach put in front of the final judge?**

If TF-IDF gets 6/6, stop there. We don't need embeddings.

If TF-IDF gets 3/6 and the explanation inventory gets 6/6, we've got empirical justification for the more interesting architecture.

That's the direction I'd explore before accepting a heavy ML dependency. The PyTorch problem may be telling us something useful: **we were reaching for a semantic-search architecture before establishing that semantic search is actually the right decomposition of the editorial problem.**
