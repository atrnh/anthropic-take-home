## Claude

I've reviewed the README and the files around it. I haven't edited anything.

**Verdict:** The README is a list of links, not a landing page. It never says what the standard is for, what the rewrite proves, or why a reviewer should care. Worse, it repeats the rewrite README, which breaks your own rule SHARE-01. A reviewer who opens Part 2 gets file names and build steps before they get a single idea.

## What's wrong, in priority order

1. **It has no argument.** Compare it with [1-audit/README.md](1-audit/README.md), which opens with claims. This page should answer three questions in about five sentences:
   - **Problem:** instructions written for one context read as if they apply everywhere. That's the audit's "Scope instructions to the reader's context" finding.
   - **Standard:** ten rules for task pages whose steps depend on context.
   - **Proof:** "Install a plugin" rebuilt as one task page with two complete workflows and a chooser.

   Right now none of that is there. "Start with the style-guide excerpt for rules on…" is directions, not a reason to read.

2. **It breaks the rule it introduces.** Lines 7–10 and 39–42 list the same before/after/decisions links twice. Lines 18–37 copy the rewrite README's view and build sections. A reviewer who notices will read it as a lapse in the exact skill being assessed.
   - Fix: keep one link list, cut "Build it yourself" to a single line pointing at [rewrite/README.md](2-standards/rewrite/README.md), and let that page own setup.

3. **The broken link at [README.md:40](2-standards/README.md:40).** `[original] [pages]` puts two links on neighbouring words, so it's unclear which is which. It also conflicts with line 8, where "before" means Cowork only. Name them: "Cowork source (the before page)" and "Government source (used for the second variant)".

4. **The NOTE is in the wrong place and weakens your credibility.**
   - It comes before the reader knows what the rewrite is.
   - "Went ahead and optimistically updated… since I'm familiar with the product" is the kind of unverified claim your own EVID-01 and UI-01 rules flag.
   - The substance is good: you updated where you had evidence and held back where you didn't. That's editorial judgment, so present it that way. For example: "The General variant uses UI labels from Claude Desktop as of 17 September, which differ from the 14 September snapshot. Government steps stay as the source wrote them because I couldn't verify them. The [method record](2-standards/rewrite/changelog.md) lists each unverified label."
   - Move this below "what changed", or make it one line in that section.

5. **"View in a browser" doesn't work where reviewers will be.** They'll most likely be on GitHub, which shows `page.html` as source code. The rewrite README admits this, but this page doesn't. The biggest usability win is a hosted preview link, via GitHub Pages or a published artifact, plus a screenshot or GIF of the chooser inline. Then nobody has to install `uv` to see the main result of Part 2.

6. **Label names drift across files.** The same variant appears as:
   - "general installation instructions" in the NOTE
   - `cowork` as its ID
   - "Claude Desktop (General)" as its label
   - "the general Cowork guide" in the question readers are told to send their admin

   On a page about helping readers identify their context, inconsistent names for the context are the one thing a sharp reviewer will catch. Pick one name and use it everywhere.

## Nearby files

- **[style-guide.md](2-standards/style-guide.md):** a five-column table with paragraphs inside the cells is hard to read on GitHub. Try one short section per rule (requirement, why, ✅/❌ example, check), or at least shorten the rationale column. Also point out that SHARE-01 is the rule Part 3's checker enforces. That link is currently one-way, from 3-check back to here.
- **[how-to-template.md](2-standards/how-to-template.md):** it mixes authoring guidance with build details: `source/page.md` owns…, the Jinja loops, and the Assembly list in the closing comment. A writer filling in the template doesn't need those. Move the build details to the rewrite README and keep the template about the reader and the evidence.
- **[changelog.md](2-standards/rewrite/changelog.md):** "Scope and challenge alignment" talks to the grader ("not completion of the entire take-home"). Cut it or move it to the log.
- **Voice:** the changelog and 3-check say "Ashley confirmed…", while this README and the audit use "I". Pick one. For a take-home, "I" reads as more honest.
- **[rewrite/README.md](2-standards/rewrite/README.md):** this is solid engineering documentation. Its one flaw is that "Try the chooser", which is the payoff, sits last, after Jinja comment syntax. Move it up to just after "View the result".
